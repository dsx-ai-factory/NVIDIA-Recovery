# PR 56 local 300-job scale report

Date: 2026-08-28  
Change under test: PR #56, `perf/sac-non-final-jobs` at `b218cfd`  
Environment: local Colima/Kind deployment, `advisor-act` profile

## Executive summary

PR #56 behaved as designed: SAC fetched the filtered Job Manager job set only
during process startup. Each SAC process made two `GetJobs` reads because its
first Slurm-active read failed and the bootstrap correctly retried on the next
tick. No later tick fetched the general JM job list.

Removing that repeated read did not make the full reconciliation loop fast at
this scale. As the campaign accumulated Advice and accounting history, completed
ticks grew from a mean of 8.7 seconds to 36.9 seconds, with a measured maximum of
46.3 seconds. One later tick remained in serial job upserts for several minutes
and had not completed when the scenario was stopped, so completed-tick metrics
understate the worst case.

The campaign also found correctness failures in 300-child fan-out waves. Release
left 12 children held, cancellation left 44 held, and cancellation after JM and
SAC recovery left 16 held. SAC's aggregate action counter reached the expected
total even though some children received no effective mutation; logs contained
duplicate executions for the same Advice/job. Correctness tests must count unique
job actions, not only the aggregate counter.

These results do not show that the PR #56 bootstrap optimization itself caused
the fan-out failures. They do show that PR #56 addresses only one source of work:
Advice-driven accounting and serial JM upserts dominate the remaining scale
cost.

## Test environment and assumptions

- Colima: 8 CPUs, 16 GiB memory, 60 GiB disk.
- Kind: one control-plane and two worker nodes.
- Slurm: two compute nodes, 16 CPUs total, no oversubscription.
- SAC: 500m CPU/256 MiB limit, 50m CPU/64 MiB request.
- SAC poll interval: 5 seconds.
- Slurm command timeout: 30 seconds.
- Advice max age: 5 minutes.
- The lightweight job requested 1 MiB memory so Slurm could use all 16 CPUs.
- “300 jobs” means 300 active scheduler records under reconciliation load. The
  local cluster could run at most 16 jobs simultaneously, not 300.
- The stack and database were intentionally reused across scenarios to expose
  history-related degradation. Results from later scenarios therefore measure
  cumulative-load behavior, not an isolated cold-start case.

## Scenario results

| Scenario | Result | Observed behavior |
| --- | --- | --- |
| 300-job scheduler/JM registration | Pass | 56.641 s to submit; 4.353 s from completed submission to JM registration; 65.804 s total including cleanup. |
| 300-child fan-out release | Fail | Timed out at 1,803.2 s. 288 children completed and 12 remained `PENDING/JobHeldUser`. The aggregate release counter reached 300, but logs showed duplicate Advice execution. |
| 300-child fan-out cancellation | Fail | Progress stopped with 44 children still `PENDING/JobHeldUser`; exact IDs were captured before cleanup. |
| JM outage and SAC restart with 300 held children | Partial/fail | JM recovered and SAC restarted. The fresh SAC process bootstrapped JM jobs, then parent cancellation removed 284 children while 16 remained held. |
| 300 independent 10-second jobs | Fail | Slurm completed all 300, but JM registered 287. Thirteen jobs completed between increasingly long observations and were never present in JM. |
| 300-parent fan-in | Fail before DAG evaluation | All parents completed, but Slurm rejected the child submission because the APS comment containing 300 dependency objects exceeded its accepted parameter/path length. Runtime: 198.5 s. |
| 300-level chain cancellation | Blocked | The first run exposed a test-oracle pagination bug after total dependency rows exceeded 1,000. After fixing the local oracle, the reused stack was still serially persisting the preceding 301-job snapshot; the new chain had not reached JM before the run was stopped. |
| 300-level chain release | Not run | It shares the same registration prerequisite as chain cancellation. Running it on the degraded stack would not isolate release behavior. |

The stopped/blocked cases are not counted as passes. Jobs created by a stopped
test were cancelled by exact captured Slurm job IDs.

## SAC tick measurements

Metrics were scraped once per second. A tick duration was derived only when the
successful reconcile counter advanced. A process restart creates a new epoch.

| SAC process epoch | Completed ticks observed | Mean | p50 | p95 | p99 | Max | Max Advice | Max accounting jobs | Peak RSS |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Initial process | 278 | 8.704 s | 8.833 s | 16.347 s | 19.372 s | 21.696 s | 901 | 901 | 39.4 MiB |
| First restart | 3 | 30.510 s | 30.898 s | 32.840 s | 33.012 s | 33.055 s | 1,202 | 1,194 | 41.2 MiB |
| Second restart | 78 | 36.878 s | 35.048 s | 45.157 s | 45.935 s | 46.272 s | 1,503 | 1,562 | 49.1 MiB |

For the final epoch, the average completed tick spent 11.460 seconds in job
status polling and 25.373 seconds in job reconciliation. Advice reconciliation
itself averaged only 0.020 seconds, but Advice identities caused targeted Slurm
accounting reads and expanded the set reconciled in the other stages.

The controller has per-command and per-operation bounds, but the campaign did
not observe a hard timeout for the entire tick or for the full serial job-upsert
stage. The configured five-second poll interval does not start a concurrent tick;
effective observation frequency becomes approximately the previous tick duration
plus the interval.

## Findings

### 1. Fan-out mutations can strand children at 300 scale

This is the highest-priority correctness finding.

- Release: 12 of 300 children remained held.
- Cancellation: 44 of 300 children remained held.
- Cancellation after JM/SAC recovery: 16 of 300 children remained held.
- Aggregate SAC action totals were not sufficient proof because the same
  Advice/job could be executed more than once.

Recommended follow-up:

1. Correlate Advice ID, job ID, and attempt index end to end.
2. Verify Advice pagination produces each expected unique key exactly once.
3. Add a unique-job action metric or assertion and retain aggregate operation
   metrics only as throughput indicators.
4. Make scheduler mutations idempotent and ensure failed/missing unique actions
   remain retryable.

### 2. Historical Advice/accounting work dominates tick duration

`GetJobs` reads stayed at startup-only levels while tick time continued to grow.
At the end of the campaign SAC was reading about 1,500 Advice records and
targeting about 1,500 accounting jobs per completed tick. The final completed
epoch averaged 36.9 seconds per tick, and a later serial-upsert pass remained in
progress for several minutes.

Recommended follow-up:

1. Stop returning Advice that is durably completed or no longer actionable.
2. Persist Advice processing state so SAC restart does not replay all history.
3. Batch or concurrently bound JM upserts instead of issuing one serial RPC per
   job.
4. Add a whole-tick deadline and stage-level backlog metrics, including in-flight
   tick age; completed-tick histograms cannot expose a currently stuck tick.

### 3. Short-lived jobs can be missed when effective polling exceeds runtime

All 300 independent jobs completed in Slurm, but only 287 appeared in JM. Their
10-second runtime was shorter than the degraded observation interval. This is a
general discovery-latency problem: startup-only `GetJobs` cannot recover a job
that neither SAC nor the separate Watcher path registered.

Recommended follow-up:

1. Use a durable incremental scheduler/accounting cursor so jobs that live
   entirely between `squeue` snapshots are still discovered.
2. Define a supported minimum observable job duration if durable discovery is
   not yet available.
3. Alert when completed Slurm accounting jobs have no corresponding JM record.

### 4. A 300-parent fan-in cannot be encoded in the Slurm comment

The child was rejected at submission with `Pathname of a file, directory or
other parameter too long`. JM and SAC never received a graph to evaluate.

Recommended follow-up: store large DAG specifications out of band and put only a
bounded workflow/job reference in the Slurm submission metadata. Until then,
document and validate a maximum dependency count before invoking `sbatch`.

### 5. The combined local deployment has an unconsumed on-demand queue

RabbitMQ reported 18,509 ready messages and zero consumers for
`on_demand_job_update_request_queue`. This queue is produced by JM's stale-job
refresh mechanism, not by SAC's direct upsert RPC. The missing consumer is a
local combined-stack issue unless the same topology exists in a deployed
environment, but it adds noise and unbounded resource growth to long-running
tests.

Recommended follow-up: either deploy the intended consumer in the local profile
or disable on-demand refresh publishing when that consumer is intentionally
absent. Add an E2E preflight assertion for queue consumer count and depth.

### 6. Scale-test observability needed corrections

The campaign found three harness problems:

- SAC restart passed a long timeout to `kubectl` but the command wrapper killed
  it after 30 seconds.
- The dependency oracle read only the first 1,000 rows, making suites
  order-dependent once accumulated rows exceeded that limit.
- Aggregate action-counter deltas could pass despite duplicate actions and
  stranded unique jobs.

The first two were corrected locally for diagnosis. They were not added to PR
#56. The unique-action assertion still needs a product-supported identifier or
metric.

## Added tick diagnostics

PR #56 adds live-progress metrics for ticks that have not completed. Completed
tick and stage latency continues to use the existing histograms:

| Metric | Purpose |
| --- | --- |
| `slurm_advisor_controller_reconcile_in_progress` | Reports whether a tick is currently running. |
| `slurm_advisor_controller_reconcile_started_timestamp_seconds` | Allows the age of an in-flight tick to be calculated before it completes. |
| `slurm_advisor_controller_reconcile_stage_in_progress{stage}` | Identifies the bounded stage currently running. |
| `slurm_advisor_controller_reconcile_stage_started_timestamp_seconds{stage}` | Allows the current stage age to be calculated. |

All labels come from bounded enums. The metrics do not contain job, workflow,
Advice, cluster, or user identifiers.

Example PromQL for the current tick age:

```promql
(time() - slurm_advisor_controller_reconcile_started_timestamp_seconds)
* slurm_advisor_controller_reconcile_in_progress
```

Example PromQL for the active stage age:

```promql
(time() - slurm_advisor_controller_reconcile_stage_started_timestamp_seconds)
* slurm_advisor_controller_reconcile_stage_in_progress
```

## PR #56 conclusion

The startup bootstrap behavior is validated: after a successful bootstrap,
normal ticks did not issue broad `GetJobs` reads, and a failed startup source read
caused a retry rather than a partial bootstrap.

The optimization is useful but insufficient as the main scale fix. Advice
retention, targeted accounting, and serial per-job upserts become the dominant
cost. The fan-out correctness failures should be investigated independently of
the broad `GetJobs` optimization, and the local queue topology must be corrected
before using this combined setup for production-capacity conclusions.
