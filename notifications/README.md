# Notifications Service

## Requirements

Python >= 3.12
uv

## Installation

Install the project using uv:

```bash
uv sync
```

## Usage

Run the server:

```bash
uv run --locked uvicorn notifications.main:app --host 0.0.0.0 --port 8080
```

and open your browser at `http://localhost:8080/docs/` to see the docs.

## Running with Docker Compose

### Run the service

After setting up the database, you can run the whole service:

```bash
docker-compose up --build
```

You should now be able to see the docs at `http://localhost:8080/docs/`.


## Tests

Run the tests with pytest:

```bash
uv run --locked pytest
```

By default, the tests will use an in-memory sqlite database.
Use the `--use-real-db` flag to run the tests against the database specified by `settings.toml`:

```bash
uv run --locked pytest --use-real-db
```

### Update the OpenAPI spec

The tests will fail if `openapi.yaml` doesn't match the spec generated by FastAPI.

Use `--update-openapi` to update the spec:

```bash
uv run --locked pytest tests/test_openapi_spec.py --update-openapi
```

After you update the OpenAPI spec, be sure to regenerate the notifications client in `recovery_libs`:

```bash
# in the recovery_libs directory:
./scripts/generate_notifications_client.sh
```

## Audit queries and scheduler-job migration

`GET /v1/audit/events` accepts either `heimdall_job_id` for an exact attempt,
or `job_id` with an optional `attempt_index`. Omitting `attempt_index` returns
all mapped attempts of that scheduler job; zero selects attempt zero. An
attempt without a job, or combining the two identity selectors, returns 422.
Queries without an identity selector remain supported. `event_type` is an
optional exact filter, alongside the existing producer, level, inclusive
Unix-microsecond time range, sort, and opaque previous/next cursors. The
default and maximum page size remain 100.

Scheduler identity is local to this deployment: the existing attempt UUID is
UUIDv5 of `job_id-attempt_index` in the URL namespace. No tenant, cluster, or
current Job Manager record is inferred. Reusing a scheduler job ID within one
deployment has the same identity limits as the existing attempt contract.

Revision `000000000004` adds nullable internal `scheduler_job_id` and an index
on `(scheduler_job_id, event_produced_at, id)`. New ingestion projects a
nonblank string job ID of at most 255 characters and a nonnegative integer
attempt only when they reproduce the envelope UUID. It does not coerce values
or mutate the payload. Missing, malformed, conflicting, or oversized identities
remain unprojected. The existing exact-attempt index and queries continue to
include those events. On MySQL 8, the projection and event-type filter use
`utf8mb4_0900_bin` to preserve case and trailing-space distinctions. The filter
converts event types to `utf8mb4` before applying the collation, so it also
supports databases whose default character set is `utf8mb3`.

### Rollout and historical backfill

Run these commands from `notifications/` with the service's normal database
and TLS settings. Test the migration against a restored database first and
schedule index creation for the database's size and DDL constraints; schema
expansion performs no historical payload rewrite.

1. Apply the additive migration before rolling out new writers. Existing
   writers can omit the nullable column throughout the rollout:

   ```bash
   uv run --locked alembic -c notifications/_migrations/alembic.ini upgrade head
   ```

2. Deploy the new Notifications writer, then run one bounded backfill batch:

   ```bash
   uv run --locked python -m notifications.audit.backfill_scheduler_job_id --batch-size 500
   ```

   Each invocation reads at most `batch_size + 1` rows, updates at most
   `batch_size` projections, and commits once. Batch size is restricted to
   1–1000. Its final JSON line reports `scanned`, `updated`, `unmappable_ids`,
   `through_id`, and `next_after_id`. Retain these reports: unmappable IDs
   identify internal rows for database investigation. Those events remain
   queryable using their original `heimdall_job_id` or job-plus-attempt
   selector. No job ID is guessed from another event or service.

3. While `next_after_id` is non-null, resume with both IDs from the prior result:

   ```bash
   uv run --locked python -m notifications.audit.backfill_scheduler_job_id \
     --batch-size 500 --after-id PREVIOUS_NEXT_AFTER_ID --through-id PASS_THROUGH_ID
   ```

   The fixed upper bound makes the pass finite while ingestion continues.
   Repeating a batch after failure is safe: only null projections are updated.
   Already projected rows and every original event field remain unchanged.

4. Drain every old writer and its in-flight transactions, then run a complete
   final pass **from the start**, omitting both IDs on its first batch. This
   catches delayed commits behind a previous cursor and old-writer rows that
   arrived after its upper bound. Repeat a complete pass to verify zero updates;
   review and retain the remaining unmappable-row reports. Enable all-attempt
   consumers only after this catch-up; earlier all-attempt reads may be partial.

For operational rollback, disable the new all-attempt consumer/read path and
keep the expanded schema, Notifications writer, and audit history. Existing
exact-ID and job-plus-attempt reads continue to work. Do not downgrade the
database or run an older Notifications binary whose Alembic history cannot
recognize revision `000000000004`. The migration's downgrade exists for
disposable migration tests; it removes the projection/index and is not the
production rollback procedure.
